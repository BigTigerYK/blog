## 1. 执行摘要

### 核心价值主张

NoCodeFlow 将 AI 编程助手从"代码补全工具"升级为**认知工作台**——一个集代码生成、文档处理、知识管理、记忆学习于一体的智能开发环境。与市面主流 AI 编程工具不同，NoCodeFlow 不仅回答问题，更**理解上下文、积累知识、持续学习**。

产品以 **MiMoCode** 为主力 AI 引擎。MiMoCode 是小米推出的 AI 编程智能体，具备代码生成、文件编辑、Shell 执行等完整能力，支持 `mimo-v2.5-pro` 等模型，并通过 Max Mode 提供高精度推理。NoCodeFlow 同时保留 Claude、OpenAI 及所有 OpenAI 兼容接口的支持，用户可根据任务需求自由切换。

## 2. 行业痛点与挑战

### 2.1 AI 编程工具的碎片化困境

当前 AI 编程市场呈现高度碎片化态势。开发者往往需要同时使用 3-5 个工具：一个用于代码补全，一个用于文档撰写，一个用于知识检索，一个用于项目管理。工具间的上下文割裂导致**信息重复输入**和**认知负荷过载**。

### 2.2 安全与合规焦虑

使用 AI 编程工具时面临三重安全顾虑：

- **数据泄露风险**：代码和文档被发送至第三方云端处理
- **权限失控**：AI Agent 获得过多系统权限，可能执行危险操作
- **审计缺失**：缺乏对 AI 操作的完整审计追踪

### 2.3 知识孤岛与经验流失

传统开发工具中，项目知识（架构决策、代码规范、业务逻辑）分散在文档、代码注释、即时通讯中。当团队成员离职或项目交接时，**关键知识随之流失**，新成员需要数周甚至数月才能恢复上下文。

### 2.4 上下文窗口的物理限制

大语言模型的上下文窗口有限（通常 128K-200K tokens），而真实项目代码库动辄数百万行。如何在有限窗口内**精准注入最相关的上下文**，是所有 AI 编程工具必须解决的核心技术挑战。

## 3. 产品概述与核心功能

NoCodeFlow 由七大核心子系统构成，形成从**感知（文档/代码）→ 认知（上下文/记忆）→ 行动（Agent/技能）**的完整闭环。

### 3.1 多模型智能代理系统

NoCodeFlow 采用**适配器模式（Adapter Pattern）**支持多种 AI 提供商，用户无需绑定单一供应商。**MiMoCode 为默认适配器**，开箱即用。

**支持的适配器类型**：

| 适配器 | 接入方式 | 默认模型 | 适用场景 |
|--------|---------|---------|---------|
| **MiMoCode**（默认） | CLI 子进程 + stream-json 解析 | mimo-v2.5-pro | 日常开发、代码生成、文件编辑、Shell 操作 |
| Claude Code | CLI 子进程 + stream-json 解析 | 用户配置 | 复杂代码生成、长对话 |
| Claude API | Anthropic SDK 直连 | 用户配置 | 高并发 API 调用、自定义模型 |
| OpenAI | OpenAI 兼容协议 | 用户配置 | 第三方提供商（DeepSeek、Gemini、Ollama 等） |

**适配器降级链**：MiMoCode → Claude Code → Claude API → OpenAI。当首选适配器不可用时自动降级，确保用户不中断工作。

**MiMoCode 核心特性**：

- **双阶段执行模式**：第一阶段禁用写入工具（`write: false, edit: false, bash: false`）进行分析，用户确认后第二阶段启用写入执行，确保 Human-in-the-Loop 安全控制
- **Max Mode 高精度模式**：通过 `--variant max` 启用高精度推理，适用于复杂架构设计和关键代码生成
- **多提供商支持**：内置小米官方模型（`xiaomi/mimo-v2.5-pro`）支持，同时支持通过 OpenAI 兼容协议接入第三方模型
- **HITL 权限拦截**：当 Agent 尝试使用被禁用的工具时，自动触发权限请求，用户可批准或拒绝
- **本地安装优先**：优先使用本地安装的 `@mimo-ai/cli`，避免 npx 环境问题
- **应用私有目录隔离**：全局配置重定向至 `userData/agent-runtimes/mimocode`，不污染用户系统环境

**其他适配器核心能力**：

- **配置文件管理**：用户可在设置中创建多个 Agent 配置文件（ClaudeProfile），每个配置文件独立设置适配器类型、API Base URL、API Key 和模型
- **流式输出**：所有适配器均支持流式输出，实时展示 Agent 生成过程
- **多代理编排**：通过 Orchestrator 支持多 Agent 协同工作
- **动态注册**：适配器注册表（AdapterRegistry）支持运行时动态注册新适配器

### 3.2 文档智能处理系统

NoCodeFlow 内置完整的文档处理管线，支持从原始文件到结构化知识的全链路转换。

**支持格式与解析引擎**：

| 格式 | 解析引擎 | 能力 |
|------|---------|------|
| PDF | pdfjs-dist | 文本提取、页面分割 |
| Word (.docx) | mammoth | 富文本转换 |
| Markdown | marked | 语法树解析 |
| 纯文本 | 内置解析器 | 编码检测、分段 |

**智能处理管线**：

1. **分块（Chunking）**：将长文档切分为语义完整的片段，支持 RAG 上下文注入
2. **元数据提取**：自动识别标题、语言、字数等结构化信息
3. **大纲提取**：构建文档的标题层级树，支持快速导航
4. **引用识别**：支持 APA、MLA、GB/T 7714、Chicago 等主流引用格式
5. **文档问答**：基于上下文检索的精准问答，附带 `[docName:page]` 引用标注

### 3.3 全文检索与知识关联

NoCodeFlow 的知识层基于 **SQLite + FTS5** 构建，提供无需向量数据库和本地模型的高性能全文检索。同时通过 Cytoscape.js 可视化引擎构建文档关联图谱，直观展示文档间的引用和概念关联。

**存储架构**：

- **documents**：文档元数据与全文索引
- **document_chunks**：FTS5 虚拟表，支持 BM25 排序
- **document_tags**：TF-IDF 加权标签（纯 JS 实现，无 LLM 依赖）
- **document_concepts**：TF-IDF + bigram 概念提取（1.5x 短语权重加成）
- **document_citations**：跨文档引用链接

**搜索管线**：

1. **查询扩展**：基于 60+ 组中英文同义词的查询扩展，采用贪心最长匹配策略处理中文分词
2. **BM25 排序**：基于 FTS5 的 BM25 算法进行相关性排序
3. **结果去重**：内容哈希去重，避免重复结果
4. **上下文扩展**：±1 chunk 邻居扩展，获取更完整的上下文
5. **相关文档推荐**：批量 OR 查询实现关联文档发现

**领域术语词典**：内置 100+ 中文领域术语，优先识别已知术语（如"机器学习"）而非 n-gram 碎片化切分。

### 3.4 统一上下文引擎

上下文引擎是 NoCodeFlow 的核心竞争力——它决定了 AI Agent 能"看到"什么信息。

**五源上下文提供者**：

| 提供者 | 数据来源 | token 预算 |
|--------|---------|-----------|
| 代码上下文 | 当前文件（100 行上限）、项目结构树（2 层深度）、CodeGraph 符号 | 动态分配 |
| 文档上下文 | 知识库中匹配用户输入的文档片段 | 动态分配 |
| 知识上下文 | 跨文档语义搜索结果 | 动态分配 |
| 记忆上下文 | 项目记忆、用户偏好、Agent 学习经验 | 动态分配 |
| 用户上下文 | 用户偏好、代码风格、写作风格 | 固定预算 |

**多信号排序算法**：

- 来源优先级权重
- 关键词重叠度
- 文档新鲜度
- 结构相关性
- 内容哈希去重

**多层压缩策略**：

- 代码骨架化（skeletonization）
- 文档密度裁剪
- 语法降噪
- 基于优先级的 token 预算裁剪

**双轨缓存机制**：

- **后台预加载**：5 分钟 TTL，1 秒防抖
- **即时组装**：从缓存直接组装上下文，零延迟响应

**提示词构建**：

- XML 隔离上下文块（`<context>...</context>`）
- System Shield 前缀防御提示词注入
- 按来源类型分组

### 3.5 持久记忆系统

NoCodeFlow 的记忆层解决了 AI 对话"失忆"的核心痛点——Agent 可以跨会话积累项目知识。

**记忆类型**：

| 类型 | 用途 | 示例 |
|------|------|------|
| project | 项目知识 | 技术栈、目录结构、编码规范 |
| user | 用户偏好 | 写作风格、代码风格、输出格式 |
| session | 会话上下文 | 对话连续性、任务进展 |
| agent | 学习经验 | 成功/失败模式、项目知识积累 |

**记忆分类**：tech_stack、directory、commands、summary、conventions、writing_style、code_style、output_format、preferences、project_knowledge、user_feedback、success_pattern、failure_pattern

**存储限制**：单条记忆 ≤10KB，每种类型 ≤1000 条。

**置信度评分**：每条记忆附带置信度分数和访问计数，系统根据使用频率动态调整记忆优先级。

**会话召回**：SessionRecallManager 在新会话启动时自动召回相关上下文，确保对话连续性。

### 3.6 技能系统（插件架构）

NoCodeFlow 的技能系统采用**基于能力的权限模型（Capability-based Permissions）**，支持安全地扩展 Agent 能力。

**核心概念**：

- **SkillDefinition**：JSON Schema 声明能力、权限、触发器、入口点
- **SkillPermission**：细粒度权限（`file:read`、`network:http`、`agent:send` 等）
- **SkillRuntime**：执行前逐项检查权限，确保安全执行
- **AdapterRegistry**：动态注册 LLM 适配器（Gemini、Ollama、OpenAI 兼容）

**技能生命周期**：安装 → 配置 → 授权 → 执行 → 日志 → 卸载

### 4.2 四大核心差异

#### 差异一：MiMoCode 驱动的认知闭环

竞品绑定单一模型供应商，NoCodeFlow 以 **MiMoCode** 为主力引擎，同时支持 Claude、OpenAI 等多供应商切换。MiMoCode 的双阶段执行模式（分析 → 确认 → 执行）实现了真正的 Human-in-the-Loop 安全控制，而 Max Mode 高精度模式确保复杂任务的输出质量。

从文档解析 → 知识提取 → 上下文组装 → Agent 交互 → 记忆积累，形成完整的认知闭环。**Agent 不仅回答问题，更持续学习和积累**。

#### 差异二：本地优先的安全架构

所有数据（文档、知识库、记忆、配置）均存储在用户本地设备。MiMoCode 运行时目录隔离在 `userData/agent-runtimes/mimocode`，不污染用户系统环境。代码和对话通过用户自有的 API Key 直连 AI 提供商，**NoCodeFlow 服务器不接触任何用户数据**。

#### 差异三：供应商无关的灵活性

通过适配器模式和动态注册表，用户可自由切换 AI 提供商。默认使用 MiMoCode（小米 AI 编程智能体），同时支持 Claude、OpenAI 以及所有 OpenAI 兼容接口（DeepSeek、Ollama、Gemini 等），**避免供应商锁定**。

#### 差异四：工程级安全防护

4 层安全机制（进程隔离 → IPC 白名单 → 路径验证 → 命令分级）确保 AI Agent 在受控环境中运行，MiMoCode 的双阶段执行模式在此基础上增加了**应用层 HITL 拦截**——Agent 分析阶段禁用所有写入工具，用户确认后才启用执行。Symlink 绕过防护、原子文件写入、提示词注入防御等细节设计，体现了**面向企业级部署的安全意识**。

## 5. 技术架构与工程实践

### 5.1 系统架构概览

NoCodeFlow 采用 **Electron 三层进程架构**，严格分离主进程、预加载脚本和渲染进程。

| 层级 | 技术栈 | 职责 |
|------|--------|------|
| 主进程（Main Process） | Node.js + TypeScript | IPC 处理、文件系统、Agent 运行时、安全沙箱、知识库 |
| 预加载脚本（Preload） | contextBridge | 安全暴露 `window.api`，IPC 通道白名单验证 |
| 渲染进程（Renderer） | React 18 + TypeScript + Zustand | UI 渲染、状态管理、用户交互 |

**安全模型**：

- `contextIsolation: true`：渲染进程与预加载脚本完全隔离
- `nodeIntegration: false`：渲染进程无法直接访问 Node.js API
- IPC 通道白名单：所有主进程 ↔ 渲染进程通信必须通过 `shared/types/ipc.ts` 中定义的通道

**[图表建议]**：此处建议插入**系统架构图**，展示三层进程 + 7 大子系统 + IPC 通道的完整拓扑。

### 5.2 MiMoCode 适配器架构

MiMoCode 适配器是 NoCodeFlow 的默认 AI 运行时，采用 CLI 子进程模式运行：

```
用户输入 → ChatPanel → IPC (AGENT_START) → MiMoCodeAdapter
  → 优先本地二进制（userData/.../node_modules/.bin/mimo），回退 npx @mimo-ai/cli
  → 参数：run --format json --model xiaomi/mimo-v2.5-pro [--variant max]
  → 第一阶段：禁用写入（mimocode.json: write=false）
  → Agent 分析并输出 → 检测到工具被禁用 → HITL 权限请求
  → 用户确认 → 第二阶段：启用写入（mimocode.json: write=true）
  → Agent 执行操作 → stream-json 事件 → IPC (AGENT_OUTPUT) → Timeline 渲染
```

**关键设计决策**：

- **双阶段执行**：通过动态写入 `mimocode.json` 配置文件控制工具可用性，第一阶段 `write/edit/bash: false`，用户批准后切换为 `true`
- **环境隔离**：`APPDATA`（Windows）/ `HOME`（Linux）重定向至应用私有目录，MiMoCode 的全局配置、缓存、插件均存储在 `userData/agent-runtimes/mimocode/`
- **模型标识组装**：`providerType` 决定前缀（`xiaomi/` 或 `openai/`），与模型名拼接为完整标识（如 `xiaomi/mimo-v2.5-pro`）
- **可用性缓存**：30 秒 TTL 缓存 `checkAvailability()` 结果，避免频繁 spawn 子进程检测版本
- **本地优先**：优先使用 `userData/agent-runtimes/mimocode/node_modules/.bin/mimo`，回退至 `npx @mimo-ai/cli`

## 6. 安全合规性

### 6.1 安全架构

NoCodeFlow 采用**纵深防御（Defense in Depth）**策略，构建四层安全屏障，MiMoCode 适配器在此基础上增加应用层 HITL 控制：

#### 第一层：进程隔离

- Electron `contextIsolation: true` + `nodeIntegration: false`
- 渲染进程无法直接访问文件系统、网络或操作系统
- 所有敏感操作必须通过 IPC 通道请求主进程执行

#### 第二层：IPC 通道白名单

- 预加载脚本严格限制 `on()` 监听器仅允许：`AGENT_OUTPUT`、`AGENT_STATUS`、`FS_WATCH`、`PERMISSION_REQUEST`
- 所有 IPC 通道在 `shared/types/ipc.ts` 中注册，未注册的通道无法通信
- IPC 响应标准化：`ipcSuccess(data)` / `ipcError(code, message)`

#### 第三层：路径验证沙箱

```
用户输入路径 → 解析绝对路径 → 工作区边界检查 → realpath 解析 → Symlink 绕过检测 → 父目录验证
```

**关键安全特性**：

- **Symlink 绕过防护**：使用 `realpath()` 解析符号链接，防止通过 symlink 指向工作区外的敏感文件
- **父目录回退验证**：当文件不存在时，递归验证父目录是否在工作区内
- **工作区隔离**：所有文件操作严格限制在用户打开的工作区目录内

#### 第四层：命令风险分级

| 风险等级 | 处理策略 | 示例 |
|---------|---------|------|
| safe | 自动执行 | `ls`、`cat`、`pwd` |
| caution | 用户确认 | 未匹配规则的未知命令 |
| dangerous | 用户确认 + 风险提示 | `rm`、`chmod`、`curl` |
| blocked | 拒绝执行 | `rm -rf /`、`dd`、`mkfs` |

#### 应用层：MiMoCode HITL 拦截

MiMoCode 适配器在四层安全架构之上，实现了**应用层 Human-in-the-Loop 控制**：

1. **第一阶段（分析）**：写入 `mimocode.json` 配置文件，禁用 `write`、`edit`、`bash` 工具。Agent 可以读取和分析代码，但无法执行任何修改操作
2. **权限拦截**：当 Agent 尝试使用被禁用的工具时，MiMoCode 返回 `invalid` 工具事件（含 `unavailable tool` 错误），适配器将其转换为 HITL 权限请求发送至前端
3. **用户确认**：前端展示权限请求对话，用户可查看 Agent 意图执行的操作，选择批准或拒绝
4. **第二阶段（执行）**：用户批准后，写入启用配置（`write/edit/bash: true`），并通过 stdin 通知 Agent 继续执行
5. **拒绝终止**：用户拒绝时，适配器立即停止 Agent 进程（SIGTERM → SIGKILL）

### 6.2 原子文件写入

文件写入操作采用**两阶段提交**模式：

1. 写入临时文件（`.nocodeflow-tmp`）
2. 原子性重命名至目标路径

确保写入过程中断不会损坏目标文件。

### 6.3 API Key 安全管理

- API Key 从明文存储迁移至加密存储
- 通过 electron-store 的安全配置管理
- 配置文件中不硬编码任何凭证

### 6.4 提示词注入防御

- System Shield 前缀：在用户输入前注入防御性系统提示
- XML 隔离：上下文块使用 XML 标签隔离，防止注入内容逃逸
- 来源分组：不同类型上下文分组注入，降低交叉污染风险

### 6.5 合规性考量

| 合规领域 | NoCodeFlow 的应对措施 |
|---------|---------------------|
| 数据本地化 | 全部数据存储在用户本地设备，不上传至 NoCodeFlow 服务器 |
| 最小权限原则 | 权限沙箱逐项检查，技能系统基于能力授权，MiMoCode 双阶段执行 |
| 审计追踪 | 快照系统记录所有 AI 文件修改，支持回溯 |
| 供应商透明 | 用户使用自有 API Key，直连 AI 提供商 |

## 7. 典型应用场景

### 7.1 MiMoCode 驱动的智能开发

**场景**：日常开发任务——代码生成、调试、重构、文件编辑。开发者需要一个既能理解代码上下文、又能安全执行操作的 AI 助手。

**NoCodeFlow 如何解决**：

- **MiMoCode 双阶段执行**：Agent 先分析代码并制定方案（禁写阶段），用户确认后再执行修改，避免意外修改
- **Max Mode 高精度**：复杂架构设计或关键代码生成时启用 Max Mode，获得更高质量的输出
- **上下文引擎**：自动感知当前文件、项目结构、相关文档，为 MiMoCode 提供精准上下文
- **快照回滚**：每次修改自动创建快照，不满意可一键恢复

### 7.2 项目开发中的知识管理

**场景**：多人协作的代码项目，项目文档、API 文档、架构设计分散在不同位置。新成员需要大量时间理解项目上下文。

**NoCodeFlow 如何解决**：

- **知识库自动索引**：导入项目文档，自动构建可检索的全文索引
- **上下文引擎**：AI Agent（MiMoCode 或其他适配器）自动感知当前文件、项目结构、相关文档，提供精准的代码建议
- **记忆系统**：Agent 跨会话积累项目知识，提问时直接获得项目上下文

### 7.3 多格式文档处理与问答

**场景**：需要处理大量 PDF、Word、Markdown 格式的文档，跨文档检索和引用追踪困难。

**NoCodeFlow 如何解决**：

- **文档智能处理**：一键导入多格式文档，自动提取结构、元数据、引用
- **跨文档问答**：基于知识库的精准问答，附带 `[docName:page]` 引用标注
- **引用关联**：自动识别 APA/MLA/GB/T 7714/Chicago 格式引用，构建文档关联网络
- **快照回滚**：AI 修改文档后可一键恢复

### 7.4 统一开发工作台

**场景**：独立开发者或小团队需要同时处理代码、文档、知识管理，工具碎片化导致效率低下。

**NoCodeFlow 如何解决**：

- **统一工作台**：代码编辑 + AI 对话 + 文档处理 + 知识管理，一个应用完成所有工作
- **多模型支持**：默认 MiMoCode 处理日常开发，按需切换 Claude 处理复杂推理
- **技能系统**：通过插件扩展能力，无需离开工作台

- Claude CLI（可选）：仅在用户主动选择 Claude Code 适配器时需要。Onboarding 流程不包含 Claude Code 配置步骤，系统不会主动引导用户配置

**安装流程**：

1. 下载对应平台安装包（Windows: .exe / Linux: .AppImage；macOS 版本规划中）
2. 运行安装程序

**适配器降级策略**：当 MiMoCode 不可用时（网络问题等），系统自动尝试下一个可用适配器，优先级为 MiMoCode > Claude Code > Claude API > OpenAI。降级时在 Agent 面板显示提示，不弹窗打扰用户。

**自动更新**：基于 GitHub Releases 的更新机制，支持 Windows 和 Linux。
